# Бот стратегии v2.1 на Rust (`v21bot`) — спецификация

Дата: 18.10.2026. Стратегия — `STRATEGY_V2_1.md`; параметры — `strategy_v2_1.json` поверх `strategy_v2.json`, оба
файла заморожены.

Основа:
- `paper/` — демо-бот v2 на Python. Его логика на архиве совпала с бэктестом: 2 002 сигнала, 229 сделок.
- `pmbot/` — заготовки на Rust: стакан и разбор ленты Polymarket.
- `maker/` — ключи, подпись ордеров, погашение выигрышей.

## 1. Цель и критерии

**Цель.** Торговать v2.1 реальными деньгами: $100 на счёте, $20 на сделку. Одновременно измерить, насколько живые
сделки отличаются от бэктеста: успевает ли бот взять ликвидность по цене сигнала.

**Критерии готовности:**
1. **Точная копия.** Прогон Rust по архиву совпадает с Python-бэктестом (§5.4).
2. **Два режима:**
   - `demo` — без ордеров;
   - `live` — ордера плюс демо-расчёт тех же сделок; по каждой живой сделке видно «демо обещало / получили» (§6).
3. **Скорость** (§9):
   - от кадра в сокете до ордера в сокете — не больше 30 мкс в 99% случаев;
   - выстрел по таймеру — не позже 50 мкс после 840.000 с.
4. **Тесты** (§10):
   - покрытие строк ядра — не меньше 95%, всего кода — не меньше 85%;
   - непокрытые строки перечислены поимённо.
5. **Защита денег.** Пределы зашиты в код; стопы и паузы описаны в §7.

**Решения пользователя (18.10.2026):**
1. Новый Rust-проект с общим ядром стратегии для прогона по архиву, демо и боевого режима (вариант A).
2. Боевой режим и демо запускаются сразу вместе: режим `live` по каждой сделке v2.1 и отправляет ордер, и считает
   демо-прогноз.
3. Демо-расчёт идёт:
   - по всем сигналам базового правила: все монеты и часы, около 45 в день;
   - на отдельном демо-счёте: $100, ставка $20, только сделки v2.1.
4. Отдельный новый аккаунт Polymarket (Deposit Wallet) только для бота, на нём только $100. Ключи пользователь сам
   кладёт в файл на сервере и в чат их не присылает.
5. Rust обновляется до последней стабильной версии: официальному клиенту Polymarket нужна версия не ниже 1.88.
6. Если свободных денег не хватает на ордер $20 с комиссией, сделки нет. Если при этом нет открытых позиций, бот
   останавливается.
7. z считается по последней пришедшей цене Binance, без ожидания закрытия секунды. Точный z пишется рядом.
8. Binance — `stream.binance.com`. Зеркало `data-stream.binance.vision` — только запасной адрес.
9. Официальный Rust-клиент Polymarket нужен только для подписи заранее и для настройки. Отправка ордера в момент
   сигнала — своя.
10. Автостоп: после 100 живых сделок при доле выигрышей ниже 80%.
11. В приёмку входит дополнительная сверка сделок v2.
12. Коммиты — только по просьбе пользователя.

**Вне рамок:**
- изменение параметров v2.1;
- другие стратегии;
- лимитные (мейкерские) ордера;
- веб-панель;
- автоматическое пополнение и вывод денег.

## 3. Факты, на которые опирается дизайн (18.10.2026)

**Polymarket** (docs.polymarket.com):
- **Серверы и доступ:**
  - серверы — AWS eu-west-2 (Лондон); ближайший регион без ограничений — eu-west-1 (Ирландия);
  - Ирландия ограничена только на сайте, API открыт; Великобритания — только закрытие позиций;
  - проверка: `GET https://polymarket.com/api/geoblock`.
- **Задержка тейкера на крипто-рынках Up/Down — 250 мс по документации.** Биржа сообщает только флаг `itode`, а не
  величину; в начале октября сканер считал 150 мс. Поэтому фактическую задержку бот меряет сам (§6.2):
  - рыночный ордер держится, затем проверяется заново и исполняется;
  - отменить его за это время нельзя;
  - ответ на `POST /order` приходит после задержки, уже с итогом.
- **Настройки рынка** — `GET /clob-markets/{condition_id}`:
  - `itode` — включена ли задержка;
  - `mts` — шаг цены, `mos` — минимальный размер;
  - `fd` — комиссия: ставка, степень, только тейкер.
- **FAK** исполняет то, что есть в стакане, остаток отменяет.
- **Рыночная покупка:**
  - `makerAmount` — доллары до комиссии; `takerAmount` = доллары ÷ предельная цена;
  - суммы — целые числа с 6 знаками;
  - точность задаёт шаг цены рынка: при шаге 0.001 у цены 3 знака, у размера 2, у суммы 5;
  - минимальный размер — `min_order_size`.
- **Живой рынок `btc-updown-15m-1792357200` (проверено 18.10.2026):**
  - `feeSchedule`: ставка 0.07, степень 1, только тейкер, ребейт 0.2;
  - `cryptoMarketConfig`: TWAP включён, окно 60 с;
  - шаг цены 0.001, минимум 5 контрактов;
  - `itode: true` — задержка тейкера включена.
- **Deposit Wallet:**
  - `signatureType = 3`; `maker` и `signer` — адрес кошелька;
  - подпись обёрнута по ERC-7739 (`TypedDataSign`, домен «DepositWallet», версия 1).
- **Поля ордера:** `salt`, `maker`, `signer`, `tokenId`, `makerAmount`, `takerAmount`, `side`, `signatureType`,
  `timestamp` (мс), `expiration` («0» для FAK), `metadata`, `builder`, `signature`. Поля верхнего уровня:
  `orderType`, `owner`, `deferExec`.
- **Ответ `POST /order`:** `success`, `errorMsg`, `orderID`, `status` (`live`, `matched`, `delayed`, `unmatched`),
  `makingAmount`, `takingAmount`, `transactionsHashes`, `tradeIDs`.
- **Статусы сделки:** `MATCHED` → `MINED` → `CONFIRMED` или `FAILED`.
- **Комиссия крипто-рынков:** `C × rate × p × (1 − p)`, ставка 0.07 — как в замороженной стратегии. Как она
  списывается с покупки — сверху в долларах или контрактами, — документация противоречит сама себе. Проверяем на
  первой сделке (§15).
- **Официальный клиент на Rust:** `rs-clob-client-v2`, крейт `polymarket_client_sdk_v2`. Нужен Rust не ниже 1.88;
  подпись через `alloy`, HTTP через `reqwest`.

**Архив и бэктест** (замеры 18.10.2026):
- **Объём:** с 18.08 — 2 748 сигналов базового правила (около 45 в день), 315 сделок v2, 201 сделка v2.1. Из них 10
  форвардных (с 15.10), все в плюсе.
- **Время входа:** 48% сделок v2.1 — ровно на 840.000 с (цена уже в коридоре, когда начинается наблюдение), 63% — в
  первую секунду.
- **Номер монеты:**
  - в 99.1% сигналов v2.1 он известен уже в момент сигнала;
  - в 0.9% (2 случая) нужно дождаться проверок других монет; оба раза бэктест пропустил монету как третью.
- **Свежесть цены Binance:**
  - по тиковым данным (67 сигналов BTC) цена старше на 100–150 мс не изменила ни одного решения по z;
  - верхняя граница — цена старше на целую секунду: меняется 2.8% решений v2.1;
  - при задержке 0.1–0.15 с ожидаем меньше 1%.
- **Ордер на $20 через 0.3 с после сигнала** (снимки стакана, `a_v21_depth.py`, 189 сделок):
  - полностью исполнился бы в 85% сделок (BTC — 90%, ETH — 73%), в среднем $17.9 из $20;
  - средняя цена на 1.4¢ выше лучшего аска;
  - через 1–5 с объём в пределах +2¢ падает с $68 до $11 (медианы).
- **Путь «событие → исполнение» из Дублина:** около 9 мс по ленте + около 12.5 мс до биржи + 250 мс задержки ≈
  270 мс. В бэктесте заложено 300 мс.

## 4. Архитектура

### 4.1 Проект

Rust-воркспейс `v21bot/` в этом репозитории, ветка `claude/trading-bot-strategy-v2-rust-b859d6`. Исполняемый файл
— один, `v21`.

| Крейт | Что внутри | Сеть, часы, файлы |
|---|---|---|
| `v21-core` | Вся логика v2.1: параметры, окно, детектор, нумерация монет, цены Binance и z, часы, решение. Плюс симуляция FAK по стакану, правила денег, доходность и статистика. | нет |
| `v21-replay` | Чтение архива (parquet), прогон через ядро, таблицы сигналов и сделок, сравнение с Python. | только файлы |
| `v21-live` | Ленты, биржа, подпись, исполнение, деньги, погашение, риск, журнал, Telegram, здоровье. | да |
| `v21-cli` | Исполняемый файл `v21` и его команды (§4.4). | — |

Ядро не знает ни о сети, ни о часах: время и события оно получает аргументами. Поэтому одно и то же ядро работает в
прогоне по архиву, вживую и в тестах.

### 4.2 Потоки живого бота

**Горячий поток.** Отдельный поток ОС, закреплён за ядром `cores.hot`, со своим циклом событий:
- **Лента Polymarket:** две копии (два соединения), обе подписаны на 6 токенов окна (Up и Down для BTC, ETH, SOL).
  Подключение — с 600-й секунды окна.
- **Сделки Binance:** `aggTrade` по BTCUSDT, ETHUSDT, SOLUSDT, одно соединение.
- **Расчёт:** стаканы, детекторы, нумерация монет, быстрое решение (§5.3).
- **Отправка:** готовые ордера и прогретое соединение с биржей. Поток записывает ордер и читает ответ.
- **Таймер** выстрела на 840.000 с.

В решающую минуту (835–871 с окна) поток опрашивает сокеты без сна. В остальное время он спит на epoll.

**Неспешный рантайм** (tokio, ядро `cores.cold`):
- Gamma: рынки окна, их правила, исходы;
- настройки рынков на бирже;
- подпись ордеров заранее — официальным клиентом;
- канал «мои сделки», баланс, погашение выигрышей;
- точное решение и демо-расчёт (§5.3, §6.2) — тем же кодом ядра, что прогон по архиву;
- риск, журнал, Telegram, часы, здоровье.

**Связь между ними:**
- очереди SPSC без блокировок в обе стороны;
- флаги «можно стрелять», «режим», «пауза», «стоп» — атомарные;
- горячий поток пересылает неспешному каждое разобранное событие ленты и каждый выстрел;
- горячий поток никогда не ждёт неспешный.

### 4.3 Режимы

Режим задаётся строкой `mode` в конфиге и меняется перезапуском.
- **`demo`:**
  - ордера не отправляются;
  - если ключи есть, ордера всё равно подписываются: так проверяется весь путь, кроме записи в сокет;
  - без ключей демо тоже работает.
- **`live`:**
  - всё, что делает `demo`, плюс настоящий ордер по каждой сделке v2.1;
  - нужен файл ключей.

## 5. Ядро и прогон по архиву

### 5.1 Ядро — перенос `paper/strategy.py` строка в строку

**Детектор монеты** (`CoinDetector`):
- Состояние на 840 с — последнее обновление стакана не позже 840 с. Без него монета в этом окне пропускается, кроме
  случая после переподключения.
- На каждом обновлении в (840; 870] сначала проверяется Up, потом Down.
- Проверка: ask этой стороны в момент «сигнал + 0.3 с» — это ask последнего обновления не позже этого момента.
  Проверку закрывает первое обновление после этого момента или ход времени.
- Если ask ≤ 0.88, проверка удачная и монета в окне закончена. Иначе наблюдение продолжается с первого обновления
  после момента исполнения.
- Пока идёт одна проверка, другая не начинается.
- Цены округляются ровно как `np.round(x, 3)`: умножение на 1000, округление половины к чётному, деление.

**Нумерация и решение** (`WindowEngine`):
- Удачные проверки нумеруются по паре (время сигнала, id токена Up).
- Причины пропуска проверяются по порядку: неудачная проверка → третья монета → вне часов → монета не торгуется (SOL)
  → нет данных Binance → z < 1.25.
- Ядро считает решения и для v2, и для v2.1: параметры v2 нужны для дополнительной сверки (§5.4).

**Цены Binance и z** (`z_score`, `Closes`):
- `close[q]` — цена последней сделки в секунде `[q, q+1)`. В секунде без сделок повторяется предыдущая цена.
- P0, EF, σ и h — формулы `ruslan_v2.binance_features` (они записаны в `STRATEGY_V2.md` §3).
- **В прогоне по архиву** суммы считаются разностью накопленных сумм по всему файлу, в том же порядке сложения, что
  numpy (`np.cumsum`). Только так z совпадает с бэктестом до 1e-9.
- **Вживую** суммы считаются в скользящем окне. Это точнее, и на пороге 1.25 результат не меняется.

### 5.2 Живые события → строки архива

События ленты превращаются в те же строки, что лежат в `data/bbo`: время биржи (мс), токен, лучшие bid и ask.
Правила — как `paper/feeds.parse_ws` и `paper/engine.py`:
- **`book`** — снимок стакана: лучший bid — максимум цен с ненулевым объёмом, лучший ask — минимум. Пустая сторона
  даёт bid 0.0 и ask 1.0.
- **`price_change`** — по каждому изменению берутся поля `best_bid` и `best_ask`.
- **Порядок и переподключение:**
  - событие старше уже применённого для этого токена отбрасывается;
  - после переподключения изменения токена игнорируются до свежего снимка.
- **Две копии ленты:**
  - каждое событие применяется один раз — из той копии, что доставила его первой;
  - порядок событий токена сохраняется;
  - способ распознать одно и то же событие в двух копиях выбирается по записанным настоящим сообщениям (§15).
- **Сверка стакана:** лучшие уровни собранного стакана сравниваются с `best_bid` и `best_ask` сервера. При
  расхождении стакан перезагружается через REST `/book` — не чаще раза в 5 с на токен.

### 5.3 Вживую на каждый сигнал два решения

**Быстрое** (горячий поток). Принимается в момент попадания в коридор, то есть в начале проверки:
- **Номер монеты:**
  - засчитаны две более ранние проверки других монет — номер 3, пропуск;
  - более ранних проверок, засчитанных и ещё идущих, вместе меньше двух — номер ≤ 2;
  - иначе бот ждёт, пока идущие проверки закроются (не дольше 0.3 с), и решает после.
- **z** — по той же формуле, что в бэктесте, с одним отличием. Формуле нужно закрытие секунды `t − 1`, где
  `t` — целая секунда сигнала. Если из-за задержки Binance эта секунда у бота ещё не закрыта, её закрытием считается
  последняя пришедшая цена. Если закрыта — берётся её настоящее закрытие, и быстрый z равен точному. Цены новее
  секунды `t − 1` в z не попадают никогда.
- **Часы** — час момента сигнала (UTC) должен быть в [0, 7). **Монета** — BTC или ETH.
- **Состояние бота:** нет паузы и стопа, правила рынка в порядке, ленты живы, денег хватает (§7.1).
- Если всё выполнено, бот стреляет (§6.1).

**Точное** (неспешный рантайм). Тот же движок, что в прогоне по архиву, на тех же событиях, по времени биржи:
- проверка закрывается через 0.3 с;
- номер монеты считается по всем закрытым проверкам;
- z — по закрытым секундам Binance. Секунда `q` закрыта, когда пришла сделка со временем ≥ `q + 1` или когда часы
  ушли за `q + 1.5` с.

Это ровно то решение, которое принял бы бэктест. Оба решения пишутся в журнал. Случаи «быстрое ≠ точное» в отчёте
идут отдельной строкой.

**Сигнал без z** (данных Binance нет или σ = 0):
- вживую он получает номер и пропускается с причиной «нет данных Binance»;
- в прогоне по архиву он выбрасывается до нумерации, как `dropna` в бэктесте.

Это расхождение описано в `paper/replay_test.py`; на архиве оно ни разу не встречалось.

### 5.4 Прогон по архиву и приёмка

**Данные:**
- `--period main`: `data/bbo/*.parquet`, `data/bn1s/{BTC,ETH,SOL}USDT.parquet`, `data/meta_15m.parquet`,
  `data/INCIDENTS.json`;
- `--period pre`: `data_pre/bbo`, `data_pre/bn1s`, `data/meta_15m_pre.parquet`, без исключения сбоев — как в
  `ruslan_v2_pre.py`.

**Окна** — как `ruslan_v2.windows()`:
- монеты BTC, ETH, SOL; исход 0 или 1;
- для `main` — старт не раньше 18.08.2026 06:00 UTC;
- исключаются окна, у которых `[старт, старт + 900 с)` пересекает сбой из `INCIDENTS.json`, расширенный на 30 минут в
  обе стороны.

**Порядок чтения** — как `ruslan_v2.book_triggers`:
- часовые файлы по очереди;
- в файле — только токены Up этих окон, по возрастанию id токена, внутри токена — по времени (устойчивая сортировка);
- детектор получает последнее обновление не позже 840 с, затем обновления в (840; 870.3], затем ход времени до
  870.3 с + 1 мс;
- первая удачная проверка токена в файле — его сигнал. Сигнал из более позднего файла заменяет более ранний (как
  `res[i] = ...`).

**z нужен только тем сигналам,** у которых секунды Binance есть с `старт − 400` до `старт + 900`.

**Доходность** — как `ruslan_v2.returns`:
- `p = min(цена + проскальзывание, 0.99)`;
- выигрыш: `1 / (p · (1 + 0.07 · (1 − p))) − 1`, проигрыш: −1;
- считается без проскальзывания и с проскальзыванием 1.4¢.

**Критерии приёмки** (любое расхождение — ошибка, исправляется до запуска):

| Что | Эталон Python | Как сравниваем |
|---|---|---|
| Сигналы базового правила | `data/ruslan_rule_all_triggers.parquet` (сейчас 2 748) | окно, монета, `t_trig`, сторона и цена — точно; z — до 1e-9; номер в окне — точно; лишних и пропавших нет |
| Сделки v2.1 — **главный критерий** | `ruslan_v2_1.is_v21` по `data/ruslan_v2_trades.parquet` (201 с 18.08) | тот же набор; `ret_top` и `ret` — до 1e-12 |
| Сделки v2 — дополнительная проверка | `data/ruslan_v2_trades.parquet` (сейчас 315) | тот же набор, та же доходность |
| Архив 07–18.08 | `data_pre/ruslan_rule_pre_triggers.parquet`, `data_pre/ruslan_v2_pre_trades.parquet` | то же самое; сделки v2.1 — 55 |
| Итоги v2.1 | вывод `ruslan_v2_1.py` | число сделок, доля выигрышей, доход на сделку с проскальзыванием, t по окнам (`alib.cl_t`) — по каждому периоду |

Прогон всего архива — не дольше 2 минут на ПК пользователя.

### 5.5 Сверка живых дней с архивом

Архив догоняет живые дни после `forward.update()` и `ruslan_v2.py` на ПК. Затем `v21 reconcile --journal FILE`
прогоняет эти окна по архиву и сравнивает с журналом. Для каждого окна и монеты он проверяет:
- совпали ли события стакана в 835–871 с;
- совпали ли сигналы, стороны, номера и решения (быстрое и точное);
- насколько различаются `t_trig`, цена и z.

Окна сбоев из `INCIDENTS.json` помечаются отдельно.

## 6. Исполнение

### 6.1 Боевой ордер

**Ордер:**
- FAK на покупку на `stake_usd` = $20 (доллары до комиссии) с пределом 0.88, подпись Deposit Wallet;
- размер в контрактах — по правилам округления для шага цены рынка;
- если размер меньше `min_order_size`, ордера нет.

**Подпись заранее:**
- на каждое окно, к 835-й секунде, готовы 4 ордера: BTC Up, BTC Down, ETH Up, ETH Down;
- у каждого готовы тело JSON и заголовки L2 (HMAC);
- с 835-й по 870-ю секунду окна бот переподписывает готовые ордера раз в секунду. Если пробный ордер покажет, что
  подпись живёт дольше (§15), переподписывать можно реже.

**Выстрел:**
- готовые байты записываются в прогретое соединение;
- биржа держит ордер 250 мс и отвечает, сколько исполнилось;
- окончательный итог приходит по каналу «мои сделки»: `CONFIRMED`, или `FAILED` — тогда позиция откатывается и
  приходит тревога;
- если канал молчит, бот спрашивает REST.

**Не больше:**
- одного входа на монету за окно;
- двух ордеров на окно (BTC и ETH), то есть $40 под риском в окне.

**Итог ордера:**

| Что случилось | Что делает бот |
|---|---|
| Исполнилось полностью или частично | позиция такая, как исполнилась; монета в окне закончена |
| Ничего не купил, и проверка через 0.3 с тоже не прошла (цена выше 0.88) | наблюдение продолжается, как в бэктесте; возможен следующий выстрел |
| Ничего не купил, но проверка прошла (бэктест сделку открыл бы) | повтора нет; сделка пишется как «упущенная» |
| Купил, но проверка не прошла (бэктест сделку не открыл бы и продолжил бы наблюдение) | позиция остаётся; расхождение пишется в журнал |

### 6.2 Демо-расчёт (в обоих режимах)

**Момент исполнения** = момент отправки + половина пути до биржи и обратно + задержка тейкера:
- **момент отправки:**
  - для настоящего выстрела — фактический;
  - для сигнала, по которому бот не стрелял, — когда он выстрелил бы: позже из двух моментов — 840.000 с и прихода
    события, давшего сигнал;
- **путь до биржи** — медиана последних замеров по прогретому соединению (лёгкий запрос раз в `warm_interval_s`);
- **задержка тейкера:**
  - фактическая — медиана «время ответа на ордер − путь до биржи и обратно» по последним 20 живым ордерам;
  - до первых живых ордеров — 250 мс по документации;
  - когда задержка измерена, демо-история пересчитывается с ней;
  - если у рынка `itode` не `true`, задержка выключена — это пауза (§7.4).

**Цена:**
- берётся стакан купленного токена на момент исполнения; бот дожидается событий ленты до этого момента;
- уровни проходятся по возрастанию до 0.88; на каждом берётся объём, пока не потрачено $20 до комиссии;
- комиссия до первой живой сделки считается сверху в долларах, по документации ордеров. Если первая сделка покажет
  другой способ, меняется одна функция, и демо-история пересчитывается.

**Для сравнения пишутся две цены:**
- цена бэктеста — ask через 0.3 с после сигнала;
- цена «без задержки» — стакан в момент сигнала.

**Где считается:**
- **на каждом засчитанном сигнале базового правила** (все монеты и часы) — ордер $20 без счёта: даёт статистику
  исполнимости;
- **в режиме `live` — по каждой сделке:** «обещало / получили» — доллары, контракты, средняя цена;
- **на каждом выстреле:** время внутри бота (нс) — кадр → стакан → решение → запись.

**Чего демо не видит:**
- чужие ордера, исполненные в ту же миллисекунду по той же цене;
- влияние нашего ордера на стакан.

Это измеряет только боевой режим.

### 6.3 Демо-счёт

- **Старт и ставка:** $100, ставка $20.
- **Сделки** — по быстрым решениям v2.1, то есть те же, что открыл бы боевой режим.
- **Исполнение** — по демо-расчёту (§6.2).
- **Расчёт** — по официальному исходу Polymarket.
- **Денежные правила** — те же, что у боевого счёта (§7.1).

## 7. Деньги и риск

### 7.1 Баланс и ставка
- **Баланс** pUSD бот берёт с биржи раз в `balance_poll_s` (30 с) и после каждого исполнения или погашения. Плюс
  своя бухгалтерия открытых позиций.
- **Свободные деньги** = баланс биржи − деньги, занятые в отправленных и ещё не завершённых ордерах.
- **Перед каждым ордером:**
  - свободных денег меньше `stake_usd + 0.50` (ордер с худшей комиссией) — сделки нет, причина «мало денег»;
  - если при этом нет открытых позиций, которые могут вернуть деньги (не рассчитанных или не погашенных), — **стоп**
    (§7.5).

### 7.2 Пределы в коде

Это константы, конфиг может их только уменьшить:
- `stake_usd` ≤ $20;
- не больше 2 ордеров на окно и 1 на монету;
- предел цены 0.88;
- монеты — только BTC и ETH;
- часы — только 00–07 UTC.

### 7.3 Погашение выигрышей
- Когда Gamma показывает, что рынок закрыт и известен исход, бот гасит выигравшие токены через ретранслятор
  Polymarket, без газа. Логика переносится из `maker/redeem.py`: адаптер CTF, пакет Deposit Wallet, подпись EIP-712.
- Повторы с растущей паузой. Если погасить не удалось за 60 минут — тревога; выигрыш можно забрать на сайте вручную.
- Пока токены не погашены, их деньги не считаются свободными.

### 7.4 Пауза (снимается сама, когда причина ушла)
- лента Polymarket или Binance молчит больше `feed_silent_ms` (2 с) в 835–870 с окна;
- у рынка не те правила: не TWAP-60, комиссия не 0.07 со степенью 1, не только тейкер, задержка тейкера выключена
  (`itode` не `true`);
- биржа на техработах;
- часы сервера разошлись с NTP больше чем на `clock_max_offset_ms` (50 мс).

### 7.5 Стоп (снимает только пользователь)

Стоп сохраняется на диске и переживает перезапуск. Причины:
- биржа отклонила ордер по нашей вине: подпись, формат, баланс, разрешения, шаг цены, размер;
- исполнение дороже 0.88;
- пришла сделка, которую бот не отправлял;
- бухгалтерия разошлась с балансом биржи больше чем на $1;
- геоблок;
- больше 3 перезапусков за 10 минут;
- денег меньше ставки и нет открытых позиций (§7.1);
- **автостоп форварда:** среди первых 100 рассчитанных живых сделок (с ненулевым исполнением) доля выигрышей ниже 80%.
  Порог и число сделок — из `strategy_v2_1.json`.

### 7.6 Аварийная остановка и команды
- Файл `STOP` на сервере (проверка каждые 100 мс) — стоп.
- Telegram, только из чата пользователя:
  - `/status` — состояние бота;
  - `/stop` — стоп;
  - `/resume` — снять паузу;
  - `/resume confirm` — снять стоп.

**Telegram** — существующий бот пользователя, только его чат:
- **вход:** `🟢 BTC Down · окно 03:15–03:30 · 0.812 · $20.00 → 24.40 шт. · демо: $20.00 по 0.809 · z 1.70`;
- **итог:** `✅ BTC Down +$4.42 · баланс $104.42` или `❌ BTC Down −$20.27 · баланс $79.73`;
- **упущенная сделка:** `⚪ ETH Up · сигнал был, исполнения нет · демо обещало $14.20 по 0.835`;

  тревоги;
- **тревоги:** паузы, стопы, непогашенный выигрыш, обе копии ленты недоступны дольше 10 с.

## 9. Скорость

**Что меряем:**
- от прихода кадра в сокет до записи ордера в сокет;
- для выстрела по таймеру — от 840.000 с по синхронизированным часам до записи ордера.

Цели — в §1. Распределения пишутся в журнал раз в минуту и меряются `v21 bench`: самый загруженный час архива
прогоняется через горячий путь с поддельным сокетом.

**Как добиваемся:**
- горячий поток закреплён за своим ядром; в решающую минуту — опрос сокетов без сна;
- на горячем пути нет выделений памяти: буферы выделены заранее; это проверяет тест со считающим аллокатором, как в
  `pmbot/tests/no_alloc.rs`;
- цены в стакане — целые тики 0.001 (`u16`), дробные числа нужны только для z;
- JSON разбирается без копирования, читаются только нужные поля: перенос `pmbot/src/hot/wire.rs`, уже проверен на
  2 425 настоящих сообщениях;
- ордера подписаны и HTTP-запросы собраны заранее; соединение с биржей прогревается раз в `warm_interval_s`;
  `TCP_NODELAY`;
- HTTP/1.1 или HTTP/2 — выбираем по замеру на сервере (§15);
- лента Polymarket, Binance и отправка — в одном потоке, без передачи между потоками;
- сборка: `lto = "fat"`, `codegen-units = 1`, `panic = "abort"`, `opt-level = 3`, `-C target-cpu=native` (собираем
  на самом сервере).

**Честная оговорка:** внутренняя обработка — микросекунды, весь путь — около 270 мс, и почти всё в нём занимают сеть и
задержка биржи. Главный выигрыш дают место (Дублин), заранее подписанный ордер, прогретое соединение и точный таймер.

## 10. Тесты

- **Модульные** — на каждый модуль всех крейтов.
- **Сверка с Python:**
  - z, P0, EF, σ и h — с колонками `cushion_bp`, `sigma_bp`, `h`, `z` из `ruslan_rule_all_triggers.parquet`;
  - детектор и нумерация монет — случаи из `paper/tests/test_strategy.py`, перенесённые в Rust;

  пропускается и пишет об этом.
- **Подпись:** наш ордер (EIP-712 с обёрткой ERC-7739) и заголовки L2 сравниваются байт в байт с официальным
  клиентом на тестовом ключе.
- **Сквозные тесты.** Локальные поддельные серверы Polymarket (лента и REST), Binance и Gamma, на них весь бот в
  обоих режимах. Сценарии:
  - выстрел на 840.000 с; сигнал посреди минуты; неудачная проверка и продолжение;

  - обрыв копии ленты посреди минуты; обрыв обеих копий;
  - частичное исполнение; «упущенная» сделка; `FAILED` после `MATCHED`;
  - отказ биржи → стоп; денег меньше ставки → стоп; сбой погашения → тревога;
  - автостоп после 100 сделок; файл `STOP`; команды Telegram;
  - перезапуск посреди окна с восстановлением из журнала.
- **Свойства** (`proptest`): стакан и детектор против простой эталонной реализации на случайных лентах.
- **Покрытие** — `cargo llvm-cov`. Цели — в §1. Отчёт со списком непокрытых строк прикладывается к каждой вехе.

## 14. Порядок работ

| Веха | Что | Где | Ворота |
|---|---|---|---|
| 1 | Ядро и прогон по архиву | ПК пользователя | приёмка §5.4 пройдена полностью |
| 2 | Живые ленты, быстрое и точное решения, демо-расчёт, журнал, отчёты, Telegram | ПК, затем сервер (ключи не нужны) | сквозные тесты зелёные; демо на сервере работает одну торговую ночь (00–07 UTC) без ошибок |
| 3 | Подпись, отправка, исполнения, деньги, погашение, риск, команды | ПК | подпись совпадает с официальным клиентом; сквозные тесты боевого режима зелёные; покрытие по §1 |
| 4 | Запуск: `setup` → `check` → пробный ордер → `live` | сервер | разрешение пользователя на пробный ордер и на запуск |

Демо из вехи 2 работает на сервере, пока делается веха 3. Боевой запуск это не задерживает: это бесплатная проверка
всего, кроме ордеров.

## 16. Риски

- **Мало сделок.** Около 3.4 сделки в день: живые итоги долго будут шумными. Автостоп после 100 сделок ограничивает
  вред.
- **Гонка на 840.000 с.** Боты в Лондоне ближе к бирже на ~12 мс. Кому достанется лучшая цена, покажет только боевой
  режим.
- **ETH:** стакан тоньше; по архиву ордер на $20 исполняется полностью в 73% случаев.
- **Правила биржи меняются:** задержка тейкера менялась несколько раз. Изменение → пауза и тревога.
- **Погашение.** Если оно не работает, деньги кончаются после 5 сделок. Бот остановится по §7.1, выигрыш можно
  забрать на сайте.
- **Ключи** — только на сервере, в файле с правами 600; в аккаунте бота — только его $100.
- **Binance — копия цены Chainlink:** исход совпадает примерно в 99% окон. Это свойство стратегии, а не бота.
